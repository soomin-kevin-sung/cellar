# Cloudflare Tunnel and Access setup

This runbook publishes one Cellar instance at one HTTPS hostname for one owner.
Use a persistent, named Cloudflare Tunnel. A Quick Tunnel (`trycloudflare.com`)
is intended only for testing and development and is **not** the protected
production setup; Cloudflare documents that distinction in
[Quick Tunnels](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/).

Keep Cellar stopped until the Access application and owner-only policy are in
place. Cellar must always listen only on `127.0.0.1:8787` (or another explicitly
configured loopback socket). Never change `bind` to a LAN address,
`0.0.0.0`, or a public address, and never open the Cellar port in an inbound
firewall or router rule.

Replace `files.example.com`, `example.cloudflareaccess.com`, and
`owner@example.com` below with your values.

## 1. Create a named Tunnel for only `http://127.0.0.1:8787`

Install a current Windows `cloudflared` build from Cloudflare's
[downloads page](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/).
In the Cloudflare dashboard, go to **Networking > Tunnels**, select
**Create a tunnel**, and give the remotely managed tunnel a durable name such
as `cellar`. Follow the Windows connector command generated by Cloudflare, but
leave Cellar stopped while completing this runbook.

This tunnel is dedicated to Cellar. Configure no private-network route and no
second service on it. Its only origin service must be the literal loopback URL
`http://127.0.0.1:8787`; do not substitute `localhost`, a LAN IP, or an HTTPS
origin. Cloudflare's current tunnel creation flow and terminology are in
[Create a tunnel (dashboard)](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/).

## 2. Attach the chosen public hostname

Open the named tunnel, then on **Routes** select **Add route** and
**Published application**. Enter the chosen subdomain and domain for
`files.example.com`, and set **Service URL** to exactly
`http://127.0.0.1:8787`. Save the route and confirm there are no other routes on
this Cellar tunnel. Cloudflare describes published application routes in the
[same tunnel setup guide](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/#2a-publish-an-application).

The public hostname is temporarily unusable because Cellar remains stopped.
Do not start Cellar or the connector for user traffic until Steps 3-5 are
complete.

## 3. Create a self-hosted Access application

In the Cloudflare dashboard, go to **Zero Trust > Access controls >
Applications**, select **Create new application**, then **Self-hosted and
private** and **Add public hostname**. Protect the entire exact hostname
`files.example.com`, without a path or wildcard, and select the identity
provider the owner will use.

Add the Access application before making the tunnel available. Access is the
public authentication boundary; the origin's JWT validation is a second,
fail-closed boundary. Follow Cloudflare's
[self-hosted public application guide](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).

## 4. Allow only the owner identity

Create one Access policy with:

- action: **Allow**;
- rule type: **Include**;
- selector: **Emails**;
- value: the owner's one exact identity-provider email, for example
  `owner@example.com`.

Do not use **Everyone**, **Emails ending in**, an entire login method, a shared
group, a **Bypass** policy, or a service-token policy for the interactive owner
application. Cloudflare Access applications deny by default, and Cloudflare's
[policy reference](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)
documents the exact-email selector and warns about broad Allow rules. Finish
creating the application only after confirming the policy contains the single
owner email.

## 5. Copy AUD, team domain, origin, and normalized email into Cellar

Map the Access and hostname values into `config.toml`:

```toml
bind = "127.0.0.1:8787"
external_origin = "https://files.example.com"
data_root = "D:/CellarData"
database_path = "D:/CellarData/.cellar/cellar.db"

[access]
team_domain = "https://example.cloudflareaccess.com"
audience = "paste-the-application-aud-tag-here"
owner_email = "owner@example.com"
```

- In the application configuration, copy **Application Audience (AUD) Tag**
  into `access.audience` exactly. Cloudflare documents its current location and
  meaning in [Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/#get-your-aud-tag).
- Set `access.team_domain` to the full HTTPS team domain,
  `https://<team-name>.cloudflareaccess.com`, with no trailing slash. It is the
  token issuer and JWKS host; see Cloudflare's
  [team-domain FAQ](https://developers.cloudflare.com/cloudflare-one/faq/getting-started-faq/#what-is-a-team-domainteam-name).
- Set `external_origin` to the exact origin of the one protected hostname:
  lower-case `https` scheme and hostname, with no path, query, fragment,
  wildcard, explicit `:443`, or trailing slash.
- Set `access.owner_email` to the same exact identity used by the **Emails**
  policy, written in normalized lower-case ASCII form. Cellar normalizes the
  configured value and the verified JWT `email` claim by trimming outer space
  and lowercasing ASCII before requiring equality. The Access token's email is
  supplied by the identity provider; Cloudflare lists that claim in its
  [application-token reference](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/#identity-based-authentication).

Cellar validates the Access assertion's signature, issuer, AUD, time bounds,
application token type, and normalized owner email. A cookie or forwarded email
header by itself is never accepted.

## 6. Run `cloudflared` separately

Start Cellar first with `CELLAR_CONFIG` pointing at the completed config. Then
start the named tunnel connector using the Windows command generated for that
tunnel, either as its own console process or independently managed Windows
service. A remotely managed tunnel needs its tunnel token to run; protect that
token as a credential. Cloudflare documents token handling in
[Tunnel permissions](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/remote-tunnel-permissions/).

Do not launch the named connector from the Cellar binary or
`scripts/check.ps1`. The two process lifecycles and their logs stay separate.
On Windows, `cloudflared` does not automatically update, so include it in the
operator's normal patch routine.

## 7. Verify all three security boundaries

Perform these checks after both processes are running:

1. **Unauthenticated redirect:** open a private/incognito browser window at
   `https://files.example.com`. It must go to Cloudflare Access authentication,
   not directly to Cellar. Do not continue if the UI is public.
2. **Authenticated UI:** sign in as the one allowed owner. The Cellar UI must
   load and its project request must succeed. Sign-in as any other identity
   must remain denied.
3. **Direct API rejection:** on the Cellar PC, bypass Cloudflare and call the
   loopback API without an assertion:

   ```powershell
   curl.exe --include http://127.0.0.1:8787/api/v1/projects
   curl.exe --include --header "Cf-Access-Jwt-Assertion: invalid" http://127.0.0.1:8787/api/v1/projects
   ```

   Both calls must return `401 Unauthorized`; the JSON error code is
   `unauthorized`. A local `CF_Authorization` cookie or
   `Cf-Access-Authenticated-User-Email` header is not a substitute for the
   signed assertion.

Cloudflare explains that it sends the signed assertion to the origin and that
the origin must validate it in
[Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).
If real Cloudflare credentials or a domain are unavailable, mark only these
public manual checks blocked. Never weaken or bypass authentication to make a
check pass.
